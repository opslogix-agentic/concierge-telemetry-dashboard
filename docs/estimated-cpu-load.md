# Estimated MR CPU load

Approved empirical display mapping: cpuLoad5 / (1000 * cpuCount). Separate resource/service cpu-load-estimate, displayed Estimated CPU load (no capacity alarms), preserves cpu-load as CPU telemetry freshness. Both require valid fresh samples. Missing/failed/stale/future observations remain UNKNOWN. Fresh valid estimates report OK regardless of magnitude; this means diagnostic data available, not capacity healthy. Values above 100 are retained without clamping.

Controller details expose raw value/core count/native observation time, formula, empirical=true, thresholds_active=false and the low-load/four-core validation limitation. No CPU warning/critical thresholds are applied. Existing configured percentage thresholds remain inactive. MR33/MR36/MR45 cross-model study: 825 unique minute-aligned pairs, observed displayed range 0–11%, median absolute display error 0.256–0.280 percentage points, maxima 0.520–0.672. Four-core-only observations do not distinguish core normalization from a fixed divisor of 4000. This is an estimated dashboard-load metric, not measured busy-time utilization.

Icinga receives estimated_cpu_load percent perfdata with empty warning/critical ranges and no upper cap. A new explicitly labeled service is added to the 28 existing MR hosts; CPU notifications remain disabled. Temperature alert delivery and all other service policies are preserved. Existing performance-data export/graphing configuration is retained; no new graph backend installed.

Dashboard shows independent live freshness/estimate cards and a 24-hour SVG trend from the protected CPU sample archive. Source readings older than the freshness limit are not published as current estimates. Historical graph retains dated archival readings, breaks gaps exceeding 30 minutes, scales above 100 when necessary, and handles absent archive without creating a database or failing the page. Archive reads are scoped by the tenant-selected device integration and serial.

Deploy through repository push/pull: controller API first, updated plugin second, Icinga host/service configuration validation/reload, then dashboard restart. No new Meraki polling, credential or database-schema migration. Revert the release commits through repository workflow if rolling back, removing new Icinga consumers before the controller resource. Preserve raw samples/history and existing freshness service identity.

The controller currently has no native Icinga time-series graph exporter enabled. Each estimated-load service therefore links through action_url to its device-specific dashboard trend anchor (/telemetry/devices/<id>/#estimated-cpu-load). Perfdata remains available, and no external graph backend is installed by this change. Dashboard authentication is required for the chart.
