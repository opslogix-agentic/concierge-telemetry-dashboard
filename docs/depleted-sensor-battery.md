# Depleted MT battery fault and dependent suppression

A current successful Meraki sensor fetch may contain old last-reported measurements. A last-reported battery of exactly zero remains CRITICAL even after the usual seven-day battery observation TTL. Output/details explicitly retain its original timestamp, reading_stale and last_reported; this is a retained known failure, not a fresh battery measurement. Failed/stale API collection, missing readings and future timestamps still yield UNKNOWN. Old nonzero battery readings remain UNKNOWN and do not suppress other faults.

Temperature and sensor-freshness checks return a transport-compatible OK with explicit SUPPRESSED/not-evaluated message and suppression metadata while latest known zero battery and missing/stale temperature correlate. This prevents duplicate child alarms but does not assert room temperature is safe. Raw last temperature and time remain available as dated metadata; no old temperature value is emitted as current perfdata. Dashboard badges display SUPPRESSED rather than green OK. A fresh temperature reading newer than the battery-zero observation bypasses suppression so real temperature breaches remain visible; a newer positive battery sample restores normal evaluation.

Battery notification routes are enabled on MT services using existing contacts/channels. Only OK/Warning/Critical states are notified; UNKNOWN battery noise remains excluded because other sensors have infrequent/absent battery samples. Other MT temperature/freshness alert policy is unchanged. Stale zero still displays 0%/CRITICAL but does not emit a fresh battery perfdata observation. Existing customer email-contact enable/disable preferences remain unchanged.
